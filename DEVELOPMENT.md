# May I Have a Room? — Development Notes

Understood as: grow the published browser game into an open-duration hotel survival loop where story, management, faction, and world-state conditions unlock player-chosen final events. Every day persists one seeded 2–6 person screening queue: procedural NORMAL survivors sustain hotel pressure, at most one condition-gated MAIN character can replace a normal slot without overt UI identification, MAIN stays remain story-controlled, and saved history carries every decision into later visits.

Aura presentation is understood as data-owned: every Aura defines its own short label, category, and icon, and room UI must never infer presentation from an NPC role.

## Next system priorities

- Complete resolution cutscenes in branch pairs: once either choice is illustrated, finish its alternate before moving to another event. Each branch must own distinct 1672×941 artwork, use canonical guest names from the guest catalog in its text and accessible description, state both the benefit and any irreversible opportunity cost in the player-facing choice copy, share the same data-driven trigger and serialized queue contract, make the same trade-off legible in its composition, and clear a built Pages preview check. Never imply that a permanent branch can be revisited unless a reachable state transition actually implements that return. For autonomy-centered resolutions, choice labels must identify whose decision is being supported or recognized; do not use permission or ownership verbs unless the mechanic genuinely gives the player that authority
- Validate generated artwork against the exact pixel contract before wiring it into game data. Verify player-facing choice copy and runtime effects independently. Any choice that says a guest permanently leaves, transfers, escapes, or is banished must use the authoritative departure contract (or an explicit multi-guest transition) and prove room, Aura, duty, visitor history, revisit policy, save restoration, and cutscene queue behavior. Never clear or claim the loss of a shared outcome flag merely to invert one producer's branch
- Keep the shared `StoryChoiceEffect.departure` architecture and iterate in place for single-guest permanent departures; it cleared Hazel's room, Aura, staff, history, revisit, save, and cutscene gates without another character-specific runtime path
- Reject a resolution branch that ends at a producer-only flag or generic one-time stat delta when its paired choice owns a recurring mechanic. The alternate must own a reachable downstream consumer or an explicit lasting state transition, and the choice copy must compare the immediate and recurring horizons before the player commits
- Treat player-facing cutscene titles as a real-surface gate: a successful build and a loadable image do not validate copy. Check the built bundle for the intended title and forbidden stale or misspelled variants before shipping
- Prioritize remaining branch pairs by verified downstream consumers, not raw flag occurrence counts; producer-only references do not prove gameplay integration
- Require every persistent story flag consumer to be proven from a reachable producer in an integration test. Boundary fixtures may set flags directly only after that producer-to-consumer route is covered, and legacy aliases must resolve to a current canonical source instead of becoming new runtime IDs
- Placement-gated resident programs must derive their targets from the same Aura range used by room UI rather than a parallel distance guess. Prove an eligible room inside the range, an eligible room outside it, an ineligible resident inside it, an absent source resident, and a stat-floor case that produces no false beneficiary or log; serialize the source choice before the DAY settlement test
- Apply economic discounts inside the same settlement function that decides affordability, shutdown, payment, and production. A post-settlement bonus or log-only rebate cannot claim it kept a facility running. Every discount must report actual paid cost and saved cost separately, prove the exact-one-short boundary where it changes availability, and prove a zero-eligible-cost state creates no benefit or log
- One-time story arrivals must be scheduled from the choice DAY, transform rather than resize the deterministic queue, consume only after an actual NORMAL slot materializes, defer when MAIN and returning visitors fill the queue, and persist completion before another DAY can generate them. When arrival modifiers stack, Visitor History must record story provenance, condition modifiers, and the player's decision in that order
- Build negative state tests from explicit boundary values rather than current catalog defaults; a "no eligible target" fixture must set the eligibility predicate false for every candidate
- Threshold mechanics must test the authoritative metric on both sides and include a counterexample where a convenient proxy such as resident count disagrees because of Aura or another upstream modifier
- Arrival-condition modifiers must state and test classification transitions, stat deltas, visible condition labels, and queue timing separately. Preserving an injury or infection classification must never be described as withholding treatment when Health recovery still occurs
